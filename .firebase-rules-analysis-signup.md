# Firestore sign-up rules analysis

This is a temporary, untracked implementation note created while repairing the
account-registration permission failure.

## Relevant access path

- `lib/sign_up.dart` authenticates the phone user, links email/password, and
  creates `users/{auth.uid}`.
- Worker registration initially creates an inactive worker, then a callable
  backend verifies the store purchase and writes subscription entitlement.
- `functions/index.js` projects eligible workers into
  `publicWorkerProfiles/{uid}`. `functions/public_worker_profile.js` keeps an
  inactive worker's `isSearchVisible` value false.
- The sign-up client also attempted to update `metadata/stats` and
  `metadata/system` in the same transaction. Those paths are intentionally
  admin-only, making the entire transaction fail.
- After verified payment, sign-up rebuilt the full profile and attempted to
  rewrite immutable/server-owned fields (`createdAt`, role, ratings, and
  subscription state).
- The pre-verification phone uniqueness check queried the private `users`
  collection. It is replaced with an owner-document check after successful
  phone authentication, avoiding PII enumeration and rules rejection.

## Rule assumptions for this repair

- `users/{uid}` contains PII and remains readable only by its owner or admins.
- A user may create only their own UID document.
- Customer and inactive worker registration are self-service roles.
- Subscription entitlement, verification/approval state, ratings, and provider
  identifiers cannot be asserted during self-service creation.
- Worker public discovery remains a server-owned projection and is invisible
  until the backend verifies entitlement.
- Global counters remain server/admin-owned; the client no longer writes them.
- Initial professional registration sends profile and schedule data only.
  Subscription entitlement and rating fields are omitted until trusted backend
  processes create them.

## Query review

The Dart codebase contains Firestore reads and writes across user subcollections,
community content, reports, metadata, chat, invoices, and administrative pages.
This change does not broaden their existing rules or query permissions. It only
changes the `users/{uid}` create predicate and removes unauthorized metadata
writes from registration.
